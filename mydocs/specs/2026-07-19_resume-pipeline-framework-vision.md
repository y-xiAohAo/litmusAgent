# Vision Spec 种子 — 简历流水线框架（SDD 项目 → 简历）

> **状态**：`SEED`（未来设想，预留落盘；未立项，不影响任何当前任务）
> **创建**：2026-07-19 | **起源**：litmusAgent 简历打磨任务（`2026-07-19_01-50_project-star-finalization.md`）中验证的方法论可复用性
> **触发条件**：用户决定启动时再走完整 SDD-RIPER-ONE 立项

## 设想一句话

对任何按 SDD-RIPER-ONE 规范开发的 git 项目（有 spec + codemap + evaluation-log），复用同一条流水线，半自动地产出对标目标岗位 JD 的简历项目描述。

## 为什么可行（litmusAgent 已验证）

本次任务的每个环节都是项目无关的：

```
证据对账（evaluation-log）→ 网络对标（简历样本）→ JD 关键词矩阵 → 逐句打磨 → 终检落盘
```

SDD-RIPER-ONE 强制沉淀了流水线全部原料：

| 简历需要 | SDD 现成产物 |
|---|---|
| 量化结果（痛点→方案→数字） | evaluation-log 优化记录（天然前后对照格式） |
| 设计决策与踩坑 | specs（每个 TD/EVAL 的根因分析） |
| 工程质量信号 | 测试基线、mypy/ruff 门禁、git 提交史 |
| 可追溯性 | Spec is Truth——数字都有出处 |

即：SDD 项目在开发过程中就在自动积累简历素材，整理成简历只是最后一公里的提炼。

## 框架形态（四层）

1. **Playbook 层**：本次 spec §7 的五轮流程（R1 对标 → R2 JD 矩阵 → R3 逐句打磨 → R4 叙述版 → R5 终检）抽象为通用模板；
2. **资产复用层**：JD 关键词库按岗位方向版本化（如 `jd-agent-engineering.md`），新项目只需增量更新；
3. **模板层**：`mydocs/resume/` 目录结构（对标分析 / 关键词矩阵 / 定稿 / 素材）原样复制；
4. **（可选）自动化层**：脚本从 evaluation-log 抽数字证据、从 specs 抽痛点，生成"证据对账表"草稿；提炼与措辞仍人工逐轮迭代。

## 前提条件（决定哪些项目能进框架）

1. **证据质量门禁**：项目必须有真实验证数据（测试/联调/对照实验），否则产出空壳；
2. **规范执行度**：spec/codemap/evaluation-log 真实维护，非摆设。

## 待决项（立项时讨论）
