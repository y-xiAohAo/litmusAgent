# Spec 种子 — 批量 E2E 评测体系（Batch E2E Benchmark）

> **状态**：`SEED`（未立项，待用户批准后走完整 SDD-RIPER-ONE 流程）
> **创建**：2026-07-19 | **起源**：评测评审中识别——现有 e2e 为场景抽查级（13 场景、小样本），统计强度不足以支撑"在 N 个任务上成功率 X%"的对外表述
> **关联**：数据红线约束——一切对外数字必须 100% 可溯源到 `docs/evaluation-log.md` 等评测记录

## 动机

- 现有证据：13 场景真实联调 + 5v5 A/B，真实但样本小（3/3、2/2 量级），面试官追问"就跑了几次？"时守得住但不硬。
- 业界对 Agent 工程能力的普遍要求包含 "benchmark 构建 / 失败模式分析"；批量评测体系本身即是核心工程亮点。

## 设想形态（讨论稿）

1. **任务集**：几十到上百个多样化编码任务（覆盖算法、文件处理、数据分析、多步链路等难度分层），任务定义 + 自动判分标准（参考答案/断言）。
2. **批量 Runner**：无人值守批量执行，支持机制开关（Planner 开/关、反思开/关）形成对照组。
3. **聚合报告**：整体成功率、平均轮数、无效调用率、失败分类分布（语法/逻辑/环境/工具偏好），输出到 evaluation-log。
4. **成本约束**：真实 LLM 调用有 token 成本，任务集规模需按预算设计；可分批跑。

## 产出价值

- 评测口径升级为 "N 个批量任务成功率 X%"（可含机制对照）；
- 失败分类分布 → 新的踩坑素材；
- 评测体系本身 = 可展示的项目组件。

## 待决项（立项时讨论）

- 任务集规模与来源（自建 vs 改编公开 benchmark）
- 判分自动化程度（沙箱断言 vs LLM-as-a-Judge）
- Token 预算上限
