## 0. 任务复述（Restate First）

- **最终目标**：让 Agent 在多步任务上自动获得 Planner 的分步推进能力，无需外部手工构造 TaskPlan。
- **当前任务单元**：LLM 自动规划（用户拍板方案 A）——`run()` 开始时先调 LLM 分解任务为 TaskPlan，再走既有 Planner 注入机制。
- **In Scope**：`PlannerConfig` 配置（默认关）、engine 自动规划 + 解析 + 兜底、CLI `--plan` 旗标、测试、真实 LLM 验证（S4 无手工计划复跑）、文档。
- **Out of Scope**：启发式拆分（方案 B）、混合触发（方案 C）、规划缓存/复用、Web UI 接入。
- **Done Contract（验证方式）**：
  1. `agent.planner.enabled=true` 时：`run()` 自动创建 TaskPlan 并注入进度（mock LLM 验证）；外部注入 planner 不被覆盖；LLM 输出无法解析时静默降级直跑。
  2. 默认 `enabled=false` 时行为零变化。
  3. **真实验证**：S4 prompt + `planner.enabled=true`（无手工计划）→ 期望 file_edit 被使用（对照基线 0/8）。
  4. 全量门禁：pytest（≥637+新增）/ mypy / ruff 全绿。

## 1. Research Findings（关键事实）

1. **接入点**：`Agent.run()` 在 `self.messages.append(user)` 后、主循环前；Planner 进度经 `_build_openai_messages()`（engine.py:551）注入 system prompt——机制全部现成，缺的是"计划从哪来"。
2. **外部启动约定**：`plan.start_next()` 由外部调用（engine.py:608 注释"如果外部已经启动了 Planner"）——自动规划必须遵循同一约定。
3. **成本**：方案 A 每 run +1 次 LLM 调用（规划 prompt ~200 tokens 输出）；用户已接受。
4. **真实验证基准**：S4 无 Planner 基线 = file_edit 0/8；S4p 手工计划 = 3/3。自动规划的成功标准是逼近 S4p。
5. **解析容错**：LLM 输出可能是 `1. xxx` / `1) xxx` / `- xxx` / 带前言后语——解析器需宽容且设 `max_steps` 上限。

## 2. Innovate

机制已由用户拍板（方案 A 全量 LLM 规划、默认关可配置、混合/启发式排除）。记录设计细节决策：
1. **规划 prompt**：要求 LLM 输出编号步骤列表（≤max_steps 步），声明"只输出步骤，不要解释"。
2. **降级链**：LLM 异常 → 直跑；解析 0 步 → 直跑；每 run 只尝试一次（防重试循环）。
3. **生命周期**：每次 `run()` 重新规划（新任务新计划）；外部注入 planner 优先且不覆盖。

class PlannerConfig(BaseModel):

    enabled: bool = False
    max_steps: int = 6

# src/agent/core/engine.py
class Agent:
    async def _maybe_create_plan(self, user_input: str) -> None:
        """planner.enabled 且无外部 planner 时，调用 LLM 把任务分解为 TaskPlan。
        失败/解析为空时静默降级（不阻塞任务直跑）；每 run 最多尝试一次。"""

    @staticmethod
    def _parse_plan_steps(text: str, max_steps: int) -> list[str]:
        """从 LLM 输出解析编号步骤描述（兼容 1. / 1) / - 前缀），上限 max_steps。"""

# src/agent/cli/agent_cli.py
# run/chat 新增 --plan 旗标：_build_agent(..., plan=True) 时强制 config.agent.planner.enabled = True
