## 2. 共性结论（多样本互证）

### 2.1 项目描述的黄金结构：痛点 → 方案 → 量化结果（S1/S3/S4/S5 一致）

- 每条职责 = **我解决了什么问题 → 我用了什么方案 → 我取得了什么成果**（S1 原话）。
- 反面：流水账式"负责 XX 设计与开发"（S1/S7 反例）、"提升效率与一致性"类无量化空话（S1/S2）。
- 量化必须具体：百分比、前后对比（"失败率从 20% 降至 2%"式表达）。

### 2.2 项目简介：具体场景 + 痛点 + 结果，一句话让人懂（S1）

- 反例："面向非结构化商务谈判场景"（抽象）→ 正例："面向企业商务谈判、催收沟通等复杂对话场景，针对成本高、策略不统一、经验难沉淀的痛点……将策略生成效率提升 70%"。

### 2.3 技术栈：按业务链路分层组织，不堆名词（S1/S2/S3）

- 按「大模型层 / 框架层 / 知识增强层 / 工程化层」归类，每个技术点带一句"用它做了什么"。
- 纯名词列表 = "跟着教程搭了个 Demo"的信号（S1）。

### 2.4 体现"设计决策与踩坑"，而非"用了什么"（S2，最犀利的一条）

- "RAG 的 chunk 策略怎么设计的、召回精度有没有评估过、幻觉怎么处理——这些才是面试官真正想听的"。
- "ReAct 和 Function Call 的区别、多步推理的 trace 怎么调试、工具选择的 prompt 怎么设计——简历里要给信号"。
- 避免"熟悉大模型应用开发""掌握 AI 辅助开发"类泛滥表达（写了等于没写）。

### 2.5 校招形式要求（S5/S6/S8）

- 一页 PDF；结构 = 教育背景 + 实习 + 项目经历 + 个人评价；项目 2-3 个、方向各有侧重。
- ATS/机筛依赖 JD 关键词：Agent、RAG、工具调用、Prompt 工程、Docker、Python 等需自然出现。
- 评论区高频追问"部署上线了吗"——个人项目的"真实运行证据"是差异化武器。

### 2.6 ⚠️ 重要警示：范文数字多为虚构示范，我们不能学

- S1 范文中的"效率提升 70%""一致性 65%→92%"是教学性虚构。本项目最大差异化恰恰是**所有数字真实可追溯**（evaluation-log 逐条对账），写作时宁可保守不可夸大。

## 3. 对本项目的映射（证据 → 简历表达）

本项目的独特位置：多数竞争者的 Agent 项目是"LangChain + RAG 拼装 Demo"（S2/S6 可见），本项目是**从零实现的框架 + 真实环境量化验证**——正好命中 S2 所说的"面试官真正想听的东西"。

| 对标要求 | 本项目对应证据（已核实） |
|---|---|
| 痛点→方案→量化 | 多步任务模型丢步骤 → 自动 Planner → 成功率 0/8→3/3；反思机制 A/B：无效调用 -26%、轮数 -32%；记忆存得住取不出 → 三层重构 → 召回 0/2→2/2 |
| 设计决策与踩坑 | mock 全绿下 6 个真实环境缺陷（docker-py 兼容性、容器 uid/gid 权限、事件循环复用、反思链路静默失效等）——"踩过坑、解决过真实问题"的直接证据 |
| 真实运行证据 | 13 场景真实 LLM 联调（非 mock），679 测试 / 91% 覆盖 / mypy 零错误 |
| 技术栈分层 | 沙箱执行层（Docker/Subprocess 双后端）/ Agent 核心层（规划、反思、记忆、压缩）/ 安全层（策略引擎、人工确认）/ 工程质量层（TDD、mypy、SDD） |
| JD 关键词 | Agent、工具调用、Function Calling、Prompt 工程、RAG（记忆检索）、Docker、Python、异步 |

## 4. 写作约束（定稿时遵守）

1. 每条 bullet 走「痛点→方案→量化结果」结构，数字只用 evaluation-log 已核实的值。
2. 项目简介第一句必须让非专家秒懂"这是什么、解决什么"。
3. 技术栈分层写，每层带"用它做了什么"。
4. 至少一处体现"设计决策/踩坑"深度信号（S2 标准）。
5. 不用虚构百分比，不用"熟悉/掌握/负责"空动词开头。
6. 篇幅：简历正文版 3-5 行 bullet；面试叙述版 ~2 分钟。
