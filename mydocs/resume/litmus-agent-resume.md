## 1. 简历正文版（简介 + 5 bullet）

**Litmus Agent｜自我纠错的代码沙箱 Agent 框架**（Python，个人项目）　github.com/y-xiAohAo/litmusAgent

覆盖「规划→执行→观察→纠错→交付」完整闭环的 Coding Agent：LLM 生成的代码在隔离沙箱中真实执行，失败时自动诊断修正；自建 122 任务批量评测体系（断言+LLM-judge+工具路径三重判分、机制臂对照、重复采样）驱动机制设计决策，累计 480+ 次真实 LLM 运行。

- **自动规划**：LLM 自动将多步任务分解为 TaskPlan 分步推进，含计划宽容解析与失败静默降级；批量对照实验（120 次真实运行）：规划机制使 L5 长链路任务成功率由 88% 提升至 98%（+10pp），错误恢复任务 0/2→2/2 稳定复现
- **自我反思**：自动归集失败工具调用的错误模式，生成修正策略注入后续决策；批量对照：反思机制使任务成功率由 88% 提升至 98%（+10pp）
- **长期记忆**：三层检索链（近期记忆兜底 + 语义重排 + 内容快照注入）+ 记忆语义搜索 + LLM 对话事实提取（用户口头陈述的事实与任务摘要也能写入记忆，T101/T102 复验 4/4）；80 次跨会话对照运行：开启记忆时 20 个两阶段任务召回率 100%（含 10 事实干扰检索与冲突更正），关闭时为 0%；100 条目压力测试下字面检索全量命中（含 30 天深埋与 15 条相似项干扰）；查询扩展（LLM 同义变体再检索）修复硬 paraphrase 检索失败，对照 8/8 vs 5/8
- **安全执行**：Docker/Subprocess 双沙箱后端 + 可配置策略引擎（workspace 边界、敏感路径拦截）+ 写操作人工确认
- **存储与缓存工程**：可插拔记忆存储层——JSONL（原型期零依赖）→ SQL（SQLAlchemy Core，SQLite 测试 / MySQL 部署）双后端，同一契约测试套件参数化复跑保证行为一致；Redis 缓存每轮记忆注入结果，generation 版本号失效 + TTL + 不可达降级
- **工程质量**：全程 TDD，786 测试 / 91% 覆盖率 / mypy 零错误

## 2. 面试叙述版（~2 分钟，约 550 字）

**S**：我想搞清楚一个 Coding Agent 要在真实环境里"活下来"需要哪些机制，而不是调 API 拼个 demo。于是从零设计并实现了 Litmus Agent：一个自我纠错的代码沙箱 Agent 框架——LLM 写的代码在隔离沙箱里真实执行，失败时自动诊断修正。

**T**：目标三层：一是完整闭环，规划、执行、观察、纠错、交付；二是工程质量到生产标准；三是每个核心机制都必须有真实环境下的量化证据，不接受"感觉能用"。

**A**：机制上实现了自动规划、自我反思、长期记忆、上下文压缩、双沙箱后端和策略引擎，全部配置驱动；工程上全程 TDD，786 个测试、91% 覆盖、mypy 零错误；验证上自建批量评测体系：122 个任务四档难度、断言加 LLM-judge 加工具路径三重判分、机制臂对照加重复采样，累计 480 多次真实 LLM 运行，用数据决定机制存废。

**R**：几个关键数字：在 L5 长链路难度下，规划机制和反思机制各自把任务成功率从 88% 提升到 98%；特别是错误恢复任务，带完整机制的 Agent 两次采样全部从权限拒绝中回退完成，拿掉规划后 0/2 全部踩雷终止。长期记忆系统在 80 次跨会话对照中，把召回率从 0% 拉到 100%，其中还包括 10 条事实里捞 2 条的干扰检索和更正覆盖旧值的冲突场景。这套评测体系本身还揪出了 6 个 mock 全绿下根本看不见的真实缺陷，比如 docker-py 版本兼容和容器 uid 权限问题——评估驱动开发的价值被它自己证明了。
